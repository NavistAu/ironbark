# Publish spec: ironbark → github.com/NavistAu/ironbark

Status: ALL decisions ratified 2026-07-23 (MADRs 0011–0016). Ready to
execute.

Goal: ironbark publicly consumable — repo on GitHub, versioned releases
producing exactly two artifacts (the Go module and the Docker image), CI a
stranger can trust, docs of implementer-grade quality in every form — with
**zero references to internal infrastructure anywhere in published content**,
and without breaking the authors' internal deployment.

Prior art: `~/ws/beachcomber` (NavistAu/beachcomber) — reuse its patterns
(develop→main release gate, workflow shapes, docusaurus scaffold). Beachcomber
layers that don't apply to a container-first server (SDKs, deb/rpm/AUR/nix,
installer shims, prebuilt binaries) are explicit non-goals.

## Verified current state

- 34 commits, single branch `main`, remote is the authors' internal forge.
- History scrub (manual, all files ever committed reviewed): **no secrets**.
  `internal/wpsign/testdata/` keys are documented throwaways. Internal-infra
  *references* (hostnames, registry paths, personal repo examples) exist in
  docs, CI config, and test fixtures — enumerated in W1.2 for removal.
- `go.mod`: `module ironbark` — not a fetchable path; blocks `go install`.
- CI: `.woodpecker.yaml` (vet/test/build on push+PR; ko publish to the
  internal registry on main). Integration tests (`-tags integration`,
  `test/integration/docker-compose.yml`, Vault 1.20 + OpenBao 2.5.5) run
  nowhere in CI today — locally only.
- Docs: strong README, `docs/SPEC.md`, `docs/DESIGN.md`, MADRs 0001–0014.
  Missing all community files: CONTRIBUTING, SECURITY, CHANGELOG, templates.
- License: AGPL-3.0 already committed.
- Name check: no meaningful GitHub collision (`ironbark` hits are zero-star
  personal repos).
- NavistAu GitHub org exists (beachcomber, homebrew-tap, lup, …). Docker
  Hub: only a legacy `navistautomatum` org exists and its slug cannot be
  renamed to `navistau` — which drove the DEC-0017 move to GHCR.

## Decisions

- **D1 — canonical home (RATIFIED, DEC-0011)**: GitHub `NavistAu/ironbark` is
  canonical. The internal forge becomes a pull mirror of GitHub so the
  authors' deployment pipeline keeps running; that relationship is internal
  configuration and is never named in published content. Repo is created
  **private first**, CI brought to green, flipped public only when the
  pre-flight gate passes.
- **D2 — history (RATIFIED, DEC-0015)**: `git filter-repo` string
  replacement across the full history — commit granularity and decision-log
  provenance preserved, zero internal strings anywhere, including history.
  `--replace-text` for blob contents AND `--replace-message` for commit
  messages (several mention the internal registry). The rewrite happens on a
  fresh clone **before the first push to the private GitHub repo**, so
  GitHub never sees a pre-rewrite object; the original repo stays archived
  internally. All hashes change — acceptable, nothing external references
  them yet. Verify gate: case-insensitive grep for internal identifiers over
  `git log -p --all` of the rewritten repo returns zero hits.
- **D3 — module path (RATIFIED)**: rename to `github.com/navistau/ironbark`
  (lowercase; GitHub is case-insensitive), rewrite internal imports. Enables
  `go install github.com/navistau/ironbark/cmd/ironbark@latest`. Vanity
  import path rejected: permanent meta-tag hosting obligation, zero benefit
  for a service.
- **D4 — CI platform (RATIFIED, amended, DEC-0014)**: GitHub Actions for
  project CI (public PR checks). `.woodpecker.yaml` is **kept as a generic
  example** — vet/test/build steps as-is; the publish step fully
  parameterized via Woodpecker secrets (registry host, repo path,
  credentials), so the file contains no infrastructure identifiers yet runs
  unmodified on any Woodpecker instance that supplies the secrets — including
  the authors' own. Header comment states it is an example/dogfood pipeline,
  not the project CI.
- **D5 — branch & release model (RATIFIED, amended, DEC-0012)**: adopt the
  beachcomber model for cross-project consistency. `develop` is the
  default/integration branch; `main` is the protected release branch;
  releases are prepared on `develop` and promoted via a release PR (the
  gate); `release.yml` fires on push to `main`, reads the version from a
  root `VERSION` file (ironbark's analogue of beachcomber's Cargo.toml —
  Go has no manifest version), tags `vX.Y.Z` on the merge commit unless
  already tagged, and publishes. Binary reports its version via
  `-ldflags -X` injection from the same file. SemVer; first public release
  **v0.1.0**.
- **D6 — registry (RE-RATIFIED 2026-07-23, DEC-0017 supersedes
  DEC-0013's registry choice)**: GHCR, `ghcr.io/navistau/ironbark`. Docker
  Hub fell through: the maintainer's pre-pricing-change org is slugged
  `navistautomatum` and the slug cannot be changed to `navistau`; a new org
  would hit current pricing. GHCR costs nothing extra and needs nothing
  external: workflow auth is the built-in `GITHUB_TOKEN` (`packages: write`
  permission), no registry secrets, no org registration (NavistAu already
  exists), no pull-rate-limit mitigation needed (DSOS application dropped
  from W5). Extras it does need: the package is created private by the
  first push and its visibility is independent of the repo's — "make the
  GHCR package public" is a flip-checklist item; connect the package to the
  repo (`org.opencontainers.image.source` annotation or package settings)
  so the package page carries the README; all documented pull commands use
  the full `ghcr.io/` path.
- **D7 — website + domain (RATIFIED, DEC-0016)**: docusaurus site, GitHub
  Pages, reusing the beachcomber scaffold; not a v0.1.0 blocker but part of
  the docs-quality bar (W4/W6). Domain: **`ironbark.foss.navist.au`** —
  establishes a reusable `*.foss.navist.au` namespace for future FOSS
  tools, zero purchase; CNAME → `navistau.github.io`; verify `navist.au`
  on the GitHub org to prevent subdomain takeover.
- **D8 — internal references (RATIFIED, superseded original scope,
  DEC-0014)**: **no references to internal infrastructure anywhere in
  published content** — not limited to one doc. Full genericization sweep is
  W1.2, with a mechanical verify gate.

## Execution authority and go-live mechanics (added 2026-07-30)

The maintainer has authorized autonomous execution of **everything up to,
but not including, the public flip**:

- **GitHub repo creation/management**: via `gh` CLI — create
  `NavistAu/ironbark` private, configure settings, branch protection,
  secrets. The **public flip itself remains user-confirmed**, as do all W5
  announcements (per-item).
- **DNS**: via the authors' internal DNS IaC tooling (per-domain OpenTofu
  IaC, declared-set authority model). The `ironbark.foss.navist.au` CNAME →
  `navistau.github.io` is a declared record in the existing `navist.au`
  kit: edit `navist.au/tofu/main.tf`, then `task plan:navist.au` →
  `task deploy:navist.au` per that kit's runbook.
- **Website conditionality (D7 reopened — see W4)**: if a website is
  built at all, it happens **pre-flip**, and it MUST be registered as a
  tracked site in the authors' internal analytics tooling (Umami-based)
  with the tracking script embedded — an untracked site is not an option.
- Implementation is delegated to cheaper-model subagents working from this
  spec; Fable does the reasoning/review, not the mechanical edits.

## Workstreams

### W1 — repo-local prep (no GitHub dependency; do first)

1. Module rename per D3; all imports updated. Verify: `go vet ./... && go
   test ./...` green; `go build ./cmd/ironbark` produces a binary.
2. **Genericization sweep (D8).** Replace every internal-infra and personal
   identifier with generic exemplars (`forge.example.com`,
   `registry.example.com`, `acme/widgets`-style org/repo, generic toolbox
   image names). Known sites (from grep, may not be exhaustive — the verify
   gate is the authority):
   - `.woodpecker.yaml` — publish step reparameterized per D4 (registry
     host/repo/creds all `from_secret`; `KO_DEFAULTBASEIMAGE` stays, it is a
     public value).
   - `README.md` — worked examples (`acme/widgets` policy/KV paths).
   - `docs/DESIGN.md`, `docs/woodpecker-secret-mechanisms.md` — hostnames,
     example payloads, internal-context asides.
   - `docs/plans/*`, `docs/research/*`, `docs/reviews/*` — including THIS
     file; genericize or prune before the public flip.
   - Test fixtures: `internal/policy/policy_test.go`,
     `internal/identity/parse_test.go` (mechanical rename of example
     org/repo constants).
   Verify gate: case-insensitive grep over the tracked tree for the internal
   domain and personal username returns **zero** hits (git authorship
   metadata exempt). Add the grep to the pre-flight checklist verbatim.
3. Branch model migration per D5: create `develop` from `main`; `VERSION`
   file (`0.1.0`); wire `-ldflags -X` version injection (build docs +
   `.woodpecker.yaml` + release workflow use the same flag).
4. Community files:
   - `CHANGELOG.md` — Keep a Changelog format, seeded with `Unreleased`
     summarizing M1.
   - `CONTRIBUTING.md` — dev setup (mise, go 1.24), unit vs `-tags
     integration` suites (docker compose prerequisite), branch workflow
     (develop→main, mirrors beachcomber's CONTRIBUTING), pointer to decision
     log + SPEC as normative.
   - `SECURITY.md` — supported-versions table (latest minor only), private
     reporting via GitHub Security Advisories (enable the repo setting),
     expected-response window. Secret-handling tool: launch blocker.
   - `.github/ISSUE_TEMPLATE/` — bug (asks for Woodpecker + Vault/OpenBao
     versions, redaction reminder) and feature templates.
   - `.github/dependabot.yml` — `gomod` + `github-actions`, weekly.
5. README polish: badges (CI, release), Install section — exactly the two
   artifacts: `docker pull ghcr.io/navistau/ironbark` and `go install
   github.com/navistau/ironbark/cmd/ironbark@latest` — worded
   forward-compatibly until v0.1.0 exists.
6. `docs/releasing.md` — beachcomber-style checklist adapted: bump `VERSION`,
   write CHANGELOG section, docs-currency check, release PR develop→main,
   merge-is-the-release, verify-publish steps (docker pull, `go install`,
   `cosign verify`, release page).

### W2 — GitHub repo + CI

1. Run the DEC-0015 filter-repo rewrite on a fresh clone (after W1 lands,
   so HEAD and history genericize together); verify the history grep gate;
   only then create `NavistAu/ironbark` **private** and push `main` +
   `develop`; default branch `develop`; iterate CI to green; flip public
   only at the pre-flight gate.
2. `.github/workflows/ci.yml` on push+PR to `develop` and `main`:
   - vet + build + unit tests with race detector.
   - lint job: `golangci-lint`, minimal config — don't retrofit style.
   - **integration job**: `go test -tags integration ./test/integration/...`
     against the docker-compose Vault 1.20 + OpenBao 2.5.5 services (ubuntu
     runners have docker). Single biggest trust upgrade over current CI.
3. Repo settings: description ("Woodpecker CI secret extension federating
   pipeline identity to Vault/OpenBao"), topics (`woodpecker-ci`, `vault`,
   `openbao`, `secrets`, `ci-cd`, `security`). **Deferred to the flip
   checklist** (unavailable on a private repo under the org's plan):
   branch protection on `main` (require all CI jobs; the release gate) and
   `develop` (require CI), and private vulnerability reporting (a
   public-repo feature). Org domain verification for `navist.au` can
   happen any time.
4. Verify: green checks on a test PR; protection blocks a red merge into
   `main`.

### W3 — release pipeline (`.github/workflows/release.yml`, on push to `main`)

0. No registry prerequisites (DEC-0017): auth is the workflow's
   `GITHUB_TOKEN` with `packages: write`; no external secrets, no org
   registration.
1. Beachcomber-shaped `gate` job: read `VERSION`, skip if `vX.Y.Z` already
   tagged, `workflow_dispatch` + `force` for re-release. Tag is created
   in-run with the default `GITHUB_TOKEN` (nothing triggers off the tag).
2. Image job: ko build `./cmd/ironbark` →
   `ghcr.io/navistau/ironbark:{vX.Y.Z,latest}`,
   `--platform=linux/amd64,linux/arm64`,
   `KO_DEFAULTBASEIMAGE=gcr.io/distroless/static-debian12:nonroot` (lockstep
   with Dockerfile stage-2, same constraint as today), ko's SPDX SBOMs on,
   version ldflags from `VERSION` via the repo's `.ko.yaml`
   (`builds.ldflags` templating `{{.Env.VERSION}}` — ko has no ldflags CLI
   flag; export `VERSION=$(cat VERSION)` before `ko build`),
   `org.opencontainers.image.source` annotation pointing at the repo (links
   the package page to the repo/README). The first release's push creates
   the package **private** (package visibility is independent of repo
   visibility) — making it public is a one-time step in the v0.1.0
   verify-publish checklist (docs/releasing.md), before step 5's anonymous
   pull check.
3. Sign: cosign keyless (GitHub OIDC) over the image. Document the
   `cosign verify` invocation in README + SECURITY.md — for a tool whose job
   is credential custody, signed provenance is table stakes.
4. GitHub Release: created by the workflow from the CHANGELOG section for
   the version. The Go module artifact is the tag itself — nothing else to
   publish.
5. Verify (after v0.1.0 on the public repo, from a clean machine):
   `docker run ghcr.io/navistau/ironbark:v0.1.0` starts and fails clean on
   missing config (anonymous pull — proves the package is public);
   `go install ...@v0.1.0` resolves and builds; `cosign verify` passes;
   release page shows the changelog; `--version` (or startup log) reports
   0.1.0; package page shows the README (source annotation worked).

### W6 — docs quality gate (blocking the public flip)

Docs in all forms must be implementer-grade. Concretely:

1. **Deploy-from-scratch walkthrough test**: follow README + docs only, on a
   clean environment (Woodpecker + Vault dev instance), no reference to
   author memory. Every command runs as written; every config var name
   checked against `internal/config`.
2. **Cross-doc consistency pass**: README ↔ SPEC ↔ DESIGN ↔ website say the
   same thing about the operator contract (token-role fields, policy naming,
   KV tiers, TTL semantics); one normative source (SPEC) with the others
   explicitly deferring.
3. **Example coherence**: after W1.2 genericization, all docs use the SAME
   generic exemplar org/repo so a reader can follow one thread end-to-end.
4. **Gap check**: an implementer FAQ exists for the known footguns already
   documented (ALLOWED_HOSTS, fail-open, `token_ttl` silent drop, `$ref`
   GET-only, TTL budgeting) — discoverable, not buried.

### W5 — announce / discoverability (post-v0.1.0; **every item needs explicit
per-item confirmation** — these post under user identity to third-party venues)

- PR to `woodpecker-ci/awesome-woodpecker` (secret-extension section).
- Woodpecker docs secret-extension page: ask/PR a link to known
  implementations if such a list exists.
- OpenBao community channels (few tools integration-test against OpenBao
  explicitly; they tend to amplify that).
- Optional: Show HN / lobste.rs, r/selfhosted, r/devops.

## Explicit non-goals for this publish

- **Prebuilt release binaries** — artifacts are exactly the Go module and the
  Docker image (DEC-0013). `go install` covers the binary want.
- Helm chart / kustomize overlay — a `deploy/` example manifest dir is a
  worthwhile fast-follow; chart maintenance is a commitment; defer.
- Terraform module for Vault-side onboarding + `ironbark doctor` — M2,
  already the roadmap, not a publish gate.
- OS packaging (deb/rpm/AUR/nix/homebrew) — doesn't fit a container-first
  server. Revisit only on demand.
