# Publish spec: ironbark → github.com/NavistAu/ironbark

Status: draft for review — decisions marked **[decide]** need ratification, each
ratified decision gets a MADR in `docs/decisionlog/`.

Goal: ironbark publicly consumable — repo on GitHub, versioned releases with a
pullable container image, CI a stranger can trust, docs a stranger can deploy
from — without buying a domain and without breaking the existing internal
(forge.example.com) deployment.

Prior art: `~/ws/beachcomber` (NavistAu/beachcomber) — reuse its patterns
(workflow shapes, docusaurus scaffold, release-gate ideas) where they fit;
ironbark is a smaller, container-first server, so several beachcomber layers
(SDKs, deb/rpm/AUR/nix packaging, installer shims) intentionally do not apply.

## Verified current state

- 34 commits, single branch `main`, remote `git@forge.example.com:ironbark/ironbark.git`.
- History scrub (manual, all files ever committed reviewed): **clean**. No
  secrets; `internal/wpsign/testdata/` keys are documented throwaways; all
  `acme`/`widgets`/`example.com` occurrences are worked examples or CI config,
  not credentials. `docs/woodpecker-secret-mechanisms.md` describes internal
  infra context (ci.example.com, namespace layout) — harmless but see [decide] D8.
- `go.mod`: `module ironbark` — not a fetchable path; blocks `go install`.
- CI: `.woodpecker.yaml` (vet/test/build on push+PR; ko publish to
  `forge.example.com/ironbark/ironbark` on main). Integration tests
  (`-tags integration`, `test/integration/docker-compose.yml`, Vault 1.20 +
  OpenBao 2.5.5) run nowhere in CI today — locally only.
- Docs: strong README, `docs/SPEC.md`, `docs/DESIGN.md`, 10 MADRs. Missing all
  community files: CONTRIBUTING, SECURITY, CHANGELOG, issue templates.
- License: AGPL-3.0 already committed.
- Name check: no meaningful GitHub collision (`ironbark` hits are zero-star
  personal repos). No `ironbark` on pkg.go.dev of note.
- NavistAu org exists (beachcomber, homebrew-tap, lup, …); GitHub Pages +
  custom-domain pattern already proven there (beachcomber.sh).

## Decisions

- **D1 — canonical home [decide]**: GitHub `NavistAu/ironbark` becomes
  canonical; `forge.example.com/ironbark/ironbark` becomes a Forgejo **pull mirror**
  so the internal Woodpecker deploy pipeline keeps running unchanged.
  Recommended: yes. Alternative (push-mirror from Forgejo out to GitHub) makes
  public PRs second-class — reject.
- **D2 — history [decide]**: publish full history as-is (it is clean and the
  decision log narrative has value). Recommended: yes, after a mechanical
  `gitleaks git` pass as belt-and-braces. Alternative: squash-fresh — loses
  provenance for no gain.
- **D3 — module path [decide]**: rename to `github.com/navistau/ironbark`
  (lowercase; GitHub is case-insensitive), rewrite internal imports. Enables
  `go install github.com/navistau/ironbark/cmd/ironbark@latest`. Vanity import
  path (`ironbark.foss.navist.au/...`) rejected: permanent meta-tag hosting
  obligation for zero user benefit on a service.
- **D4 — CI platform [decide]**: GitHub Actions for public CI (PRs from
  strangers must get checks; Woodpecker can't provide that on GitHub). Keep
  `.woodpecker.yaml` in-repo as the internal deploy pipeline and honest
  dogfooding — add a header comment saying it is the authors' deployment, not
  the project CI. Recommended: yes.
- **D5 — release model [decide]**: tag-driven — pushing `vX.Y.Z` runs the
  release workflow. Single-maintainer trunk-based repo; beachcomber's
  develop→main release-gate model is more ceremony than this project needs
  today (revisit if a second maintainer arrives). SemVer, first public release
  **v0.1.0** (contract is spec'd but young; pre-1.0 signals it).
- **D6 — registry [decide]**: `ghcr.io/navistau/ironbark`. Free, org-linked,
  `GITHUB_TOKEN`-authenticated from Actions. Docker Hub rejected (rate limits,
  second credential). Internal `forge.example.com` registry publishing continues via
  the Woodpecker pipeline, independent.
- **D7 — website + domain [decide]**: yes, but not a launch blocker (parallel
  workstream). Docusaurus, reusing the beachcomber scaffold; GitHub Pages;
  custom domain `ironbark.foss.navist.au` (user proposal — good: establishes a
  reusable `*.foss.navist.au` namespace for future tools, zero purchase; CNAME
  record → `navistau.github.io`, `CNAME` file in the Pages artifact, verify
  `navist.au` on the org to prevent subdomain takeover). Shorter alternative
  `ironbark.navist.au` if the `foss` layer feels noisy — user's call.
- **D8 — `docs/woodpecker-secret-mechanisms.md` [decide]**: keep (useful
  research context, nothing sensitive) with a one-line header noting it
  predates publication and references the authors' infra. Alternative: trim
  the ci.example.com specifics.

## Workstreams

### W1 — repo-local prep (no GitHub dependency; do first)

1. Module rename per D3; all imports updated. Verify: `go vet ./... && go
   test ./...` green; `go build ./cmd/ironbark` produces a binary.
2. Community files:
   - `CHANGELOG.md` — Keep a Changelog format, seeded with an `Unreleased`
     section summarizing M1.
   - `CONTRIBUTING.md` — dev setup (mise, go 1.24), unit vs `-tags
     integration` suites (docker compose prerequisite), commit/PR
     expectations, pointer to decision log + SPEC as normative.
   - `SECURITY.md` — supported-versions table (latest minor only), private
     reporting via GitHub Security Advisories (enable "private vulnerability
     reporting" repo setting), expected-response window. This is a
     secret-handling tool; SECURITY.md is a launch blocker, not a nicety.
   - `.github/ISSUE_TEMPLATE/` — bug (asks for Woodpecker + Vault/OpenBao
     versions, redaction reminder) and feature templates. PR template optional.
   - `.github/dependabot.yml` — `gomod` + `github-actions`, weekly.
3. README polish: badges (CI, release, go report card), an Install section
   (image pull from ghcr + `go install`), link to website when live. Existing
   content stands — it is already the best doc.
4. `.woodpecker.yaml` header comment per D4.
5. `docs/releasing.md` — the ironbark analogue of beachcomber's: version bump
   points (there are few: CHANGELOG + tag), tag command, what the workflow
   publishes, verify-publish checklist.
6. MADRs for D1–D8 as ratified.

### W2 — GitHub repo + CI

1. Create `NavistAu/ironbark` **private** first; push; iterate CI to green;
   flip public only when W1+W2 verify. (Public flip is the point of no return —
   everything before it is freely revisable.)
2. `.github/workflows/ci.yml` on push+PR:
   - vet + build + unit tests (`go test ./...`), race detector on.
   - lint job: `golangci-lint` (config kept minimal; don't retrofit style).
   - **integration job**: `go test -tags integration ./test/integration/...`
     with the docker-compose Vault 1.20 + OpenBao 2.5.5 services — ubuntu
     runners have docker; this is the single biggest trust upgrade over
     current CI, where the integration matrix runs only on dev machines.
3. Repo settings: description ("Woodpecker CI secret extension federating
   pipeline identity to Vault/OpenBao"), topics (`woodpecker-ci`, `vault`,
   `openbao`, `secrets`, `ci-cd`, `security`), branch protection on `main`
   (require CI green), private vulnerability reporting on, org domain
   verification for `navist.au`.
4. Verify: green checks on a test PR; branch protection blocks a red merge.

### W3 — release pipeline (`.github/workflows/release.yml`, on `v*` tag)

1. GoReleaser: static linux/amd64 + linux/arm64 binaries (darwin optional —
   marginal for a server, cheap to include), archives, `checksums.txt`,
   GitHub Release with CHANGELOG excerpt.
2. Image: ko build `./cmd/ironbark` → `ghcr.io/navistau/ironbark`,
   `--platform=linux/amd64,linux/arm64`, tags `vX.Y.Z` + `latest`,
   `KO_DEFAULTBASEIMAGE=gcr.io/distroless/static-debian12:nonroot` (must stay
   in lockstep with Dockerfile stage-2 — same constraint as the Woodpecker
   pipeline). ko emits SPDX SBOMs by default — keep on. (GoReleaser's `kos:`
   integration can fold this into step 1; implementer's choice, one workflow
   either way.)
3. Signing: cosign keyless (GitHub OIDC) over the image and checksums.txt.
   For a tool whose job is credential custody, signed provenance is table
   stakes; document the `cosign verify` line in README/SECURITY.md.
4. Verify (after v0.1.0 on the public repo): `docker run ghcr.io/...` starts
   and fails clean on missing config; `go install ...@v0.1.0` works from a
   clean machine; `cosign verify` passes; release page has binaries +
   checksums + notes.

### W4 — website (parallel; not blocking v0.1.0)

1. `website/` docusaurus scaffold cloned from beachcomber's layout (config,
   deploy-website.yml workflow shape).
2. Content is a re-projection of existing docs, not new writing: landing page
   (the README pitch + the "why not just…" table), Deploy guide (README
   deploy + operator contract sections), Reference (config table, KV
   convention, TTL budgeting), SPEC and DESIGN as-is, decision log rendered.
3. DNS: `ironbark.foss.navist.au CNAME navistau.github.io` on navist.au;
   `CNAME` file in the site; HTTPS enforced once cert issues.
4. Verify: site live on the domain, all nav links resolve, README links to it.

### W5 — announce / discoverability (post-publish; **every item needs explicit
per-item confirmation** — these post under user identity to third-party venues)

- PR to `woodpecker-ci/awesome-woodpecker` (secret-extension section).
- Ask Woodpecker docs/community whether the secret-extension docs page links
  out to known implementations; PR if so.
- OpenBao community channels (it is one of few tools integration-tested
  against OpenBao explicitly — they tend to amplify that).
- Optional: Hacker News / lobste.rs Show post, r/selfhosted, r/devops.

## Explicit non-goals for this publish

- Helm chart / kustomize overlay — a `deploy/` example manifest dir is
  worthwhile fast-follow, but chart maintenance is a commitment; defer.
- Terraform module for Vault-side onboarding + `ironbark doctor` — that's M2,
  already the roadmap, not a publish gate.
- OS packaging (deb/rpm/AUR/nix/homebrew) — beachcomber-ism that doesn't fit a
  container-first server. Revisit only on demand.

## Sequencing

```
W1 (local prep) ─┬─→ W2 (private repo, CI green) ─→ flip public ─→ W3 tag v0.1.0
                 └─→ W4 website ────────────────────────────────────┘ (any time after public)
                                                     W5 announce (after v0.1.0, confirmed per item)
```

Pre-flight gate before the public flip: `gitleaks git` clean over full
history; D8 resolved; README install instructions true (they reference
artifacts that exist only after v0.1.0 — either stage the README change with
the tag or word it forward-compatibly).
